# Git Tracker

[git-tracker.delino.io](https://git-tracker.delino.io) で Git コミットの数値測定値を追跡できます。Git Tracker は無料です。フォークからのプルリクエストを含め、公開および非公開の GitHub リポジトリに対応しています。ファイルサイズ、所要時間、スループット、件数などのスカラー測定値に利用できます。

## リポジトリを接続する

1. Delino アカウントでサインインし、個人用または組織用のスペースを選択します。
2. スペースのオーナーに依頼し、スペースのグループを通じて Git Tracker の View、Edit、Manage のいずれかの権限を付与してもらいます。View では読み取りが可能です。Edit ではさらにアップロードと完了処理が可能になります。Manage ではさらに接続、トークン管理、完全削除が可能になります。
3. リポジトリに Git Tracker GitHub App をインストールします。
4. **リポジトリを管理**を開きます。`owner/repository` と、リンク済みの GitHub アカウントの、リポジトリ管理者アクセス権を持つ GitHub アクセストークンを入力します。サービスは GitHub での権限を確認しますが、そのアクセストークンは保持しません。
5. リポジトリを接続します。Delino スペースの Owner/Admin 権限も必要です。リポジトリを同時に接続できるスペースは 1 つだけです。Action や API の呼び出しに使用するため、リポジトリ管理から接続 ID をコピーしてください。接続解除後は、権限のある別のスペースが新しい接続 ID で接続できます。元のスペースに保持された履歴は非公開のままです。

公開リポジトリの測定値は、サインインせずに閲覧できます。非公開の測定値には、スペースのメンバー資格と Git Tracker の読み取り権限が必要です。スペースのアクセス権は、そのスペースに接続されているすべてのリポジトリに適用されます。

接続を解除するか App を削除すると、アップロードが停止し、保持されている履歴は非公開になります。権限を持つメンバーは引き続き閲覧できます。公開から非公開への変更が確認されると、過去のデータも非公開になります。GitHub で現在の公開状態を確認できない場合、Git Tracker は同期が成功するまで、最後に確認された公開状態を維持します。

## データセットを定義する

リポジトリに YAML 設定を保存します。ID は固定で、名前は変更しても履歴を失いません。行内のすべての列は、まとめてアップロードする必要があります。

```yaml
id: file-size
name: JavaScript file sizes
columns:
  - id: original
    name: Original size
    unit: B
    direction: lower
    absoluteThreshold: 1024
  - id: minified
    name: Minified size
    unit: B
    direction: lower
    percentageThreshold: 1
  - id: gzip
    name: Gzipped size
    unit: B
    direction: lower
    absoluteThreshold: 128
    percentageThreshold: 2
```

JSON 形式の行をアップロードします。たとえば、SWC スタイルのファイルサイズ表は次のようになります。

```json
{
  "rows": [
    { "id": "jquery", "name": "jQuery", "values": { "original": 285314, "minified": 87533, "gzip": 30321 } },
    { "id": "three", "name": "Three.js", "values": { "original": 1321000, "minified": 675000, "gzip": 170000 } }
  ]
}
```

Action は、二進浮動小数点数への変換を行わずに、JSON の十進数表記を保持します。Connect を直接呼び出す場合は、`"9007199254740993.0000000000000001"` のように十進数値を文字列として送信します。負の数と有限小数に対応しています。表示上の丸めによってリグレッション判定が変わることはありません。

対応する単位は、`B`、`kB`、`MB`、`GB`、`KiB`、`MiB`、`GiB`、`ns`、`μs`、`ms`、`s`、`count`、`%`、`unitless`、および `ops/s`、`B/s`、`kB/s`、`MB/s`、`GB/s`、`KiB/s`、`MiB/s`、`GiB/s` です。互換性のある単位は比較前に変換されます。互換性のない種類同士は比較できません。たとえば、1048576 B は 1 MiB と表示されますが、正確な値は表で引き続き確認できます。

方向は `lower`、`higher`、`neutral` です。neutral の列ではリグレッションは発生しません。しきい値は列内のすべての行に適用されます。絶対値とパーセンテージの両方のしきい値がある場合、どちらか一方を超えるとリグレッションになります。しきい値と等しい場合は該当しません。しきい値がない場合、変化は表示されますが、リグレッションによる失敗は発生しません。悪化する方向の変化のみが判定対象です。

変化率は `(new - baseline) / abs(baseline) * 100` です。ベースラインがゼロの場合、変化率はありません。絶対値のしきい値があれば引き続き判定できますが、パーセンテージのみのルールでは判定を保留します。比較には、後から変更された設定ではなく、対象の実行に保存された設定が使用されます。

## 公式 GitHub Action を使用する

`delinoio/apps/actions/git-tracker` を、レビュー済みの完全なコミット SHA に固定してください。以下のプレースホルダーを、Git Tracker の接続 ID、チェックアウトのリビジョン、Action のリビジョンに置き換えます。OIDC 用に `id-token: write` を付与します。代わりにリポジトリアップロードトークンも使用できます。その場合は GitHub シークレットとして保存し、`token` に渡してください。

```yaml
permissions:
  contents: read
  id-token: write
jobs:
  measure:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<reviewed-checkout-commit-sha>
      - run: ./measure.sh
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          repository-id: '019b0000-0000-7000-8000-000000000001'
          configuration: measurements.yaml
          measurements: measurements.json
          fail-on-regression: 'false'
  mark-as-done:
    needs: measure
    if: always()
    runs-on: ubuntu-latest
    steps:
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          operation: complete
          repository-id: '019b0000-0000-7000-8000-000000000001'
```

独立したジョブはデフォルトの実行 ID `repository_id/run_id/run_attempt` を共有し、互いに重複しない行をアップロードできます。再実行には新しい実行 ID を使用してください。Actions OIDC ではデフォルトの識別情報が必要です。カスタム実行 ID は、リポジトリトークンを使用する呼び出し元向けです。OIDC 認証情報が接続済みリポジトリに属するプルリクエストジョブでは、Action の `baseline` 入力に明示的な完全コミット SHA を設定してください。フォークの OIDC によるアップロードは PR の head に限定され、ベースラインの上書き指定やアップストリームの push 履歴への書き込みはできません。

各アップロードジョブは、自身がアップロードした行のみを判定します。デフォルトでは、リグレッションは報告されますが CI は失敗しません。リグレッション時にそのジョブを失敗させるには、`fail-on-regression: 'true'` を設定します。比較できない場合でも CI は失敗しません。完了ジョブは測定が終了したことを示すだけで、CI の成功・失敗・キャンセル状態を送信したり、集約結果による合否判定を行ったりはしません。すべてのジョブがスキップされた場合は、空の完了処理も有効です。

ネットワークエラーや一時的な API 障害では、最大 3 回再試行します。デフォルトでは、再試行後も解決しなければジョブは失敗します。代わりに警告を出して成功させるには、`warn-on-api-error: 'true'` を設定します。PR コメントの失敗は警告のみで、保存済みデータを無効にしたり、それ単独で CI を失敗させたりすることはありません。Action は詳細リンクをログに出力し、Job Summary を書き込みます。

1 つの PR コメントに、PR の最新コミットに対して最後に登録された実行の累積結果が反映されます。以前の実行はウェブの履歴で引き続き確認できます。

## Connect API を呼び出す

API のオリジンは `https://git-tracker.api.delino.io` です。Connect の JSON リクエストでは `Content-Type: application/json` と `Connect-Protocol-Version: 1` を使用します。管理者は、将来の有効期限を必須としてリポジトリトークンを発行でき、リポジトリ管理から失効させることができます。

```sh
curl --fail-with-body \
  'https://git-tracker.api.delino.io/gittracker.v1.GitTrackerService/Upload' \
  -H "Authorization: Bearer ${GIT_TRACKER_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' \
  --data-binary @upload.json
```

`upload.json` には `context`、`dataset`、`rows` を含めます。

```json
{
  "context": {
    "repositoryId": "019b0000-0000-7000-8000-000000000001",
    "executionId": "my-historical-run",
    "commit": "0123456789012345678901234567890123456789",
    "branch": "main"
  },
  "dataset": {
    "id": "size",
    "name": "Size",
    "columns": [{ "id": "bytes", "name": "Bytes", "unit": "B", "direction": "DIRECTION_LOWER", "absoluteThreshold": "1024" }]
  },
  "rows": [{ "id": "bundle", "name": "Bundle", "values": { "bytes": "1048576" } }]
}
```

同じ `context` を指定して `/gittracker.v1.GitTrackerService/Complete` を呼び出します。PR のアップロードでは `pullRequest` を含め、PR のベースブランチと head コミットを使用します。`baselineCommit` は明示的な完全ベースライン SHA を指定します。過去のコミットにも同じアップロード API を使用します。送信前に、十進数の文字列を JavaScript の `Number` を介して変換しないでください。

アップロードまたは完了処理で送信するテキストに、NUL（`\u0000`）文字を含めないでください。Git Tracker は、該当フィールドを示すクライアントエラーでこれを拒否します。その他の対応する Unicode テキストおよび制御文字は引き続き有効です。

## 実行と比較のルール

最初のアップロードで、その実行における各データセットの設定が固定されます。以降に異なる設定を送信すると拒否されます。既存の行を同一の数値で繰り返し送信する操作は冪等です。競合する値は拒否されます。バッチはアトミックです。無効な行や競合する行がある場合、そのリクエストのデータは一切保存されません。

データはすぐに**測定中**として表示されます。代表結果になるのは完了後のみです。コミットの代表結果は、リグレッションのある実行も含め、登録順で最新の完了済み実行です。古い実行が遅れて完了しても、それより新しく登録された完了済み実行に置き換わることはありません。完了処理を繰り返しても、完了時刻や順序は変わりません。

新しい測定データが保存されないまま 6 時間が経過すると、未完了の実行は**中断**になります。同一データの再送では、このタイマーはリセットされません。完了済みおよび中断済みの実行は、それ以降のアップロードを拒否します。中断済みの実行は完了処理も拒否します。代わりに新しい実行を開始してください。データは削除するまで保持されます。

PR の自動比較では、最初のアップロード時に merge-base コミットと、その代表となる完了済み実行が固定されます。ベースラインが存在しない場合、後からアップロードしても利用不可のままです。push の自動比較では、行ごとに最大 1,000 個の最も近い第一親の祖先を調べ、最初のアップロード時点までに完了した、測定済みの最も近い祖先を使用します。その範囲内に条件を満たす行の測定値がなければ、比較は利用できません。後続のジョブも同じ基準時点を使用します。表には、実際の各参照元コミットと実行が示されます。古いコミットと比較するには、明示的なベースライン SHA を設定できます。明示的な比較では、行単位で祖先にフォールバックすることはありません。

ウェブサイトの 2 コミット比較では、選択した各コミットについて、登録順で最新の完了済みブランチ実行が優先されます。コミットに完了済みのブランチ実行がない場合は、そのコミットの、登録順で最新の完了済みプルリクエスト実行を使用します。選択された比較対象の実行に保存されたデータセット設定が使用されます。新しい行・列や、欠損または互換性のないデータは比較できず、リグレッションによる失敗の原因にはなりません。削除されたベースラインデータは復元されません。存在しない行は、完了前は未収集、完了後は欠損として扱われます。

グラフでは、第一親の順序でコミットを等間隔に配置します。スキップされたコミットをまたいで実際の測定点を結び、値を引き継いだり架空の値を補ったりすることはありません。データセット、ブランチ、列、項目、日付、コミット範囲で絞り込めます。正確な値や、キーボードでアクセスできる実行リンクはデータ表を使用してください。

## 削除とトラブルシューティング

管理者は、確認後にリポジトリの測定値、データセット、または 1 件の実行を完全に削除できます。不明な実行や、現在測定値のないデータセットを削除しようとすると、対象が見つからないと報告されます。データセットの削除は、そのデータセットを含んでいた実行にのみ影響します。他の実行では、そのデータセットを引き続きアップロードできます。ベースラインの測定値が削除された比較は利用できなくなりますが、ベースラインにそのデータセットが最初から含まれていなかった場合は、新しいデータとして扱われます。Delcore がスペースの削除を確定すると、Git Tracker はそのスペースの接続、トークン、設定、履歴を削除します。

権限エラーの場合は、選択したスペースと現在の Git Tracker ロールを確認してください。アップロードの競合では、実行の識別情報、データセット設定、行の完全な値を確認してください。中断済みまたは完了済みの実行では、新しい実行 ID を使用してください。ネットワークやサーバーのエラーでは、再試行し、サポートを求める際のためにレスポンスの相関 ID を保持してください。公開の報告でトークン、認証情報、非公開の測定値を共有しないでください。

PR 実行の測定値は引き続き確認できますが、アップストリームブランチのグラフ上の点や自動ベースラインには使用されません。これにより、共有コミット SHA に対して、フォークの測定値がベースラインブランチのデータや設定を置き換えることを防ぎます。
