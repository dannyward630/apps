# Git Tracker

[git-tracker.delino.io](https://git-tracker.delino.io) で Git コミットの数値測定値を追跡できます。Git Tracker は無料です。フォークからのプルリクエストを含め、公開および非公開の GitHub リポジトリに対応しています。ファイルサイズ、所要時間、スループット、件数、その他のスカラー測定値に利用できます。

## リポジトリを接続する

1. Delino アカウントでサインインし、個人または組織のスペースを選択します。
2. スペースの所有者に依頼し、スペースのグループを通じて Git Tracker の View、Edit、Manage のいずれかの権限を付与してもらいます。View は読み取りを許可します。Edit はアップロードと完了処理も許可します。Manage はさらに接続、トークン管理、完全削除を許可します。
3. 対象リポジトリに Git Tracker GitHub App をインストールします。
4. **リポジトリの管理**を開きます。`owner/repository` と、リポジトリの管理者アクセス権を持つ連携済み GitHub アカウントの GitHub アクセストークンを入力します。サービスは GitHub 上の権限を確認し、そのアクセストークンは保持しません。
5. リポジトリを接続します。Delino スペースの Owner/Admin 権限も必要です。リポジトリが同時に接続できるスペースは 1 つだけです。Action と API の呼び出し用に、リポジトリ管理から接続 ID をコピーします。接続解除後は、権限を持つ別のスペースが新しい接続 ID で接続できます。以前のスペースに保持されている履歴は非公開のままです。

公開リポジトリの測定値は、サインインせずに読み取れます。非公開の測定値には、スペースのメンバーシップと Git Tracker の読み取り権限が必要です。スペースのアクセス権は、そのスペースに接続されたすべてのリポジトリに適用されます。

接続を解除するか App を削除すると、アップロードが停止し、保持されている履歴は非公開になります。権限を持つメンバーは引き続き読み取れます。公開から非公開への変更が確認されると、過去のデータも非公開になります。GitHub が現在の公開状態を確認できない場合、Git Tracker は同期が成功するまで最後に確認された公開状態を維持します。

## データセットを定義する

リポジトリに YAML 設定を保存します。ID は固定で、名前は履歴を失わずに変更できます。行内のすべての列はまとめてアップロードする必要があります。

```yaml
id: file-size
name: JavaScript file sizes
columns:
  - id: original
    name: Original size
    unit: B
    direction: lower
    absoluteThreshold: 1024
  - id: minified
    name: Minified size
    unit: B
    direction: lower
    percentageThreshold: 1
  - id: gzip
    name: Gzipped size
    unit: B
    direction: lower
    absoluteThreshold: 128
    percentageThreshold: 2
```

JSON の行をアップロードします。たとえば、SWC 形式のファイルサイズ表は次のようになります。

```json
{
  "rows": [
    { "id": "jquery", "name": "jQuery", "values": { "original": 285314, "minified": 87533, "gzip": 30321 } },
    { "id": "three", "name": "Three.js", "values": { "original": 1321000, "minified": 675000, "gzip": 170000 } }
  ]
}
```

Action は、2 進浮動小数点数への変換を行わずに、JSON の 10 進数表記を保持します。Connect を直接呼び出す場合は、`"9007199254740993.0000000000000001"` のように 10 進数値を文字列として送信します。負数と有限小数に対応しています。表示上の丸めがリグレッション判定に影響することはありません。

対応する単位は、`B`、`kB`、`MB`、`GB`、`KiB`、`MiB`、`GiB`、`ns`、`μs`、`ms`、`s`、`count`、`%`、`unitless`、および `ops/s`、`B/s`、`kB/s`、`MB/s`、`GB/s`、`KiB/s`、`MiB/s`、`GiB/s` です。互換性のある単位は比較前に変換されます。互換性のない種類は比較できません。たとえば、1048576 B は 1 MiB と表示されますが、表では正確な値を確認できます。

方向には `lower`、`higher`、`neutral` があります。neutral の列ではリグレッションは発生しません。しきい値は列内のすべての行に適用されます。絶対値とパーセンテージの両方のしきい値がある場合、どちらかを超えるとリグレッションになります。等しい場合は該当しません。しきい値がない場合、変化は表示されますが、リグレッションによる失敗は発生しません。悪化する方向の変化だけが判定されます。

変化率は `(new - baseline) / abs(baseline) * 100` です。ベースラインがゼロの場合、変化率は算出されません。その場合も絶対値のしきい値では判定できますが、パーセンテージのみのルールでは判定を保留します。比較には、後からの設定ではなく、対象の実行に保存された設定が使用されます。

## 公式 GitHub Action を使用する

`delinoio/apps/actions/git-tracker` を、レビュー済みの完全なコミット SHA に固定してください。以下のプレースホルダーを、Git Tracker の接続 ID、チェックアウトのリビジョン、Action のリビジョンに置き換えます。OIDC 用に `id-token: write` を付与してください。代わりにリポジトリアップロードトークンも使用できます。GitHub シークレットとして保存し、`token` に渡してください。

```yaml
permissions:
  contents: read
  id-token: write
jobs:
  measure:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<reviewed-checkout-commit-sha>
      - run: ./measure.sh
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          repository-id: '019b0000-0000-7000-8000-000000000001'
          configuration: measurements.yaml
          measurements: measurements.json
          fail-on-regression: 'false'
  mark-as-done:
    needs: measure
    if: always()
    runs-on: ubuntu-latest
    steps:
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          operation: complete
          repository-id: '019b0000-0000-7000-8000-000000000001'
```

独立したジョブはデフォルトの実行 ID `repository_id/run_id/run_attempt` を共有し、互いに重複しない行をアップロードできます。再実行には新しい実行 ID を使用してください。Actions OIDC ではデフォルトの識別子が必須で、カスタム実行 ID はリポジトリトークンによる呼び出し用です。フォークの OIDC アップロードは PR のヘッドに限定され、ベースラインの上書きを指定したり、上流のプッシュ履歴に書き込んだりすることはできません。

各アップロードジョブは、自身がアップロードした行のみを判定します。デフォルトでは、リグレッションは報告されますが CI は失敗しません。リグレッション時にそのジョブを失敗させるには、`fail-on-regression: 'true'` を設定します。比較できない場合も CI は失敗しません。完了ジョブは測定が終了したことだけを示し、CI の成功・失敗・キャンセルの送信や、集計結果に基づくゲート判定は行いません。すべてのジョブがスキップされた場合、データのない完了処理も有効です。

ネットワークエラーと一時的な API 障害は、最大 3 回再試行されます。デフォルトでは、再試行後にジョブが失敗します。代わりに警告を出して成功させるには、`warn-on-api-error: 'true'` を設定します。PR コメントの失敗は警告のみで、保存済みデータが無効になったり、それ自体で CI が失敗したりすることはありません。Action は詳細リンクをログに出力し、ジョブサマリーを書き込みます。

1 つの PR コメントに、その PR の最新コミットで最後に登録された実行の累積結果が反映されます。以前の実行も Web の履歴で引き続き確認できます。

## Connect API を呼び出す

API のオリジンは `https://git-tracker.api.delino.io` です。Connect の JSON リクエストでは `Content-Type: application/json` と `Connect-Protocol-Version: 1` を使用します。管理者は、将来の有効期限を必須で設定したリポジトリトークンを発行し、リポジトリ管理から取り消すことができます。

```sh
curl --fail-with-body \
  'https://git-tracker.api.delino.io/gittracker.v1.GitTrackerService/Upload' \
  -H "Authorization: Bearer ${GIT_TRACKER_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' \
  --data-binary @upload.json
```

`upload.json` には `context`、`dataset`、`rows` を含めます。

```json
{
  "context": {
    "repositoryId": "019b0000-0000-7000-8000-000000000001",
    "executionId": "my-historical-run",
    "commit": "0123456789012345678901234567890123456789",
    "branch": "main"
  },
  "dataset": {
    "id": "size",
    "name": "Size",
    "columns": [{ "id": "bytes", "name": "Bytes", "unit": "B", "direction": "DIRECTION_LOWER", "absoluteThreshold": "1024" }]
  },
  "rows": [{ "id": "bundle", "name": "Bundle", "values": { "bytes": "1048576" } }]
}
```

同じ `context` で `/gittracker.v1.GitTrackerService/Complete` を呼び出します。PR のアップロードでは `pullRequest` を含め、PR のベースブランチとヘッドコミットを使用します。`baselineCommit` は、明示的な完全なベースライン SHA を選択します。過去のコミットにも同じアップロード API を使用します。送信前に、10 進数文字列を JavaScript の `Number` 経由で変換しないでください。

## 実行と比較のルール

最初のアップロードで、その実行における各データセットの設定が固定されます。その後に異なる設定を送信すると拒否されます。同一の数値を持つ既存の行を再送信する操作はべき等です。矛盾する値は拒否されます。バッチはアトミックです。無効な行または矛盾する行がある場合、そのリクエストのデータは一切保存されません。

データは直ちに**測定中**として表示されます。代表結果となるのは完了後のみです。コミットの代表結果は、そのコミットで最後に登録された完了済みの実行であり、リグレッションを含む実行も対象になります。古い実行が遅れて完了しても、より新しく登録された完了済みの実行を置き換えることはありません。完了処理を繰り返しても、完了時刻と順序は変わりません。

測定データが新たに保存されない状態が 6 時間続くと、未完了の実行は**中断**になります。同一データの再送信では、このタイマーはリセットされません。完了済みおよび中断された実行は、それ以降のアップロードを拒否します。中断された実行は完了処理も拒否します。代わりに新しい実行を開始してください。データは削除するまで保持されます。

PR の自動比較では、最初のアップロード時にマージベースのコミットと、その代表となる完了済みの実行が固定されます。ベースラインが存在しない場合、後からアップロードしても利用不可のままです。プッシュの自動比較では、行ごとに第 1 親の祖先をたどり、最初のアップロード時点の締め切りまでに完了した、測定済みの最も近い祖先を使用します。後続のジョブも同じ締め切りを使用します。表には、実際の参照元の各コミットと実行が示されます。明示的なベースライン SHA による比較では、行単位で祖先へのフォールバックは行いません。

Web サイトの 2 コミット比較では、選択した各コミットについて、最後に登録された完了済みのブランチ実行を優先します。コミットに完了済みのブランチ実行がない場合、そのコミットで最後に登録された完了済みのプルリクエスト実行を使用します。選択された比較対象の実行に保存されているデータセット設定が使用されます。新しい行や列、および欠損データや互換性のないデータは比較できず、リグレッションによる失敗の原因にはなりません。削除されたベースラインデータは復元されません。存在しない行は、完了前には未収集、完了後には欠損として扱われます。

グラフでは、第 1 親の順序でコミットを等間隔に配置します。測定されていないコミットをまたいで実際の測定点を結び、値を引き継いだり作り出したりすることはありません。データセット、ブランチ、列、項目、日付、コミット範囲で絞り込めます。正確な値や、キーボードでアクセスできる実行リンクにはデータ表を使用してください。

## 削除とトラブルシューティング

管理者は、確認後にリポジトリの測定値、データセット、または 1 つの実行を完全に削除できます。ベースラインが削除された比較は利用できなくなります。Delcore がスペースの削除を確定すると、Git Tracker はそのスペースの接続、トークン、設定、履歴を削除します。

権限エラーの場合は、選択中のスペースと現在の Git Tracker ロールを確認してください。アップロードの競合の場合は、実行の識別情報、データセット設定、行の値がすべて揃っていることを確認してください。中断または完了した実行には、新しい実行 ID を使用してください。ネットワークエラーやサーバーエラーの場合は再試行し、サポートを求める際のためにレスポンスの相関 ID を保持してください。公開の報告でトークン、認証情報、非公開の測定値を共有しないでください。

PR 実行の測定値は引き続き確認できますが、上流ブランチのグラフの点や自動ベースラインには使用されません。これにより、フォークの測定値が、同じコミット SHA に対するベースラインブランチのデータや設定を置き換えることを防ぎます。
