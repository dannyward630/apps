# Git Tracker

[git-tracker.delino.io](https://git-tracker.delino.io) で Git コミットの数値測定値を追跡できます。Git Tracker は無料です。フォークからのプルリクエストを含め、公開および非公開の GitHub リポジトリに対応しています。ファイルサイズ、所要時間、スループット、件数、その他のスカラー測定値に利用できます。

## リポジトリを接続する

1. Delino アカウントでサインインし、個人または組織のスペースを選択します。
2. スペースのオーナーに依頼し、スペースのグループを通じて Git Tracker の View、Edit、Manage のいずれかの権限を付与してもらいます。View は読み取りを許可します。Edit では、さらにアップロードと完了操作が可能になります。Manage では、さらに接続、トークン管理、完全削除が可能になります。
3. リポジトリに Git Tracker GitHub App をインストールします。
4. **リポジトリを管理**を開きます。`owner/repository` と、リポジトリの管理者権限を持つ、連携済み GitHub アカウントの GitHub アクセストークンを入力します。サービスは GitHub 上の権限を検証しますが、そのアクセストークンは保持しません。
5. リポジトリを接続します。Delino スペースの Owner/Admin 権限も必要です。リポジトリは一度に 1 つのスペースにのみ接続できます。Action および API 呼び出し用に、リポジトリ管理から接続 ID をコピーします。接続解除後は、権限を持つ別のスペースが新しい接続 ID で接続できます。元のスペースに保持された履歴は非公開のままです。

公開リポジトリの測定値は、サインインせずに閲覧できます。非公開の測定値を閲覧するには、スペースのメンバーであり、Git Tracker の読み取り権限を持っている必要があります。スペースのアクセス権は、そのスペースに接続されたすべてのリポジトリに適用されます。

接続を解除するか App を削除すると、アップロードが停止し、保持されている履歴が非公開になります。権限を持つメンバーは引き続き閲覧できます。公開から非公開への変更が確認されると、履歴データは非公開になります。GitHub で現在の公開状態を確認できない場合、Git Tracker は同期が成功するまで、最後に確認された公開状態を維持します。

## データセットを定義する

リポジトリに YAML 設定を保存します。ID は固定で、名前を変更しても履歴は失われません。行内のすべての列は、まとめてアップロードする必要があります。

```yaml
id: file-size
name: JavaScript file sizes
columns:
  - id: original
    name: Original size
    unit: B
    direction: lower
    absoluteThreshold: 1024
  - id: minified
    name: Minified size
    unit: B
    direction: lower
    percentageThreshold: 1
  - id: gzip
    name: Gzipped size
    unit: B
    direction: lower
    absoluteThreshold: 128
    percentageThreshold: 2
```

JSON 形式の行をアップロードします。たとえば、SWC スタイルのファイルサイズ表は次のようになります。

```json
{
  "rows": [
    { "id": "jquery", "name": "jQuery", "values": { "original": 285314, "minified": 87533, "gzip": 30321 } },
    { "id": "three", "name": "Three.js", "values": { "original": 1321000, "minified": 675000, "gzip": 170000 } }
  ]
}
```

Action は、二進浮動小数点への変換を行わずに、JSON の十進数表記を保持します。Connect を直接呼び出す場合は、`"9007199254740993.0000000000000001"` のように十進数値を文字列として送信します。負の数と有限小数に対応しています。表示上の丸めがリグレッション判定を変えることはありません。

対応する単位は、`B`、`kB`、`MB`、`GB`、`KiB`、`MiB`、`GiB`、`ns`、`μs`、`ms`、`s`、`count`、`%`、`unitless`、および `ops/s`、`B/s`、`kB/s`、`MB/s`、`GB/s`、`KiB/s`、`MiB/s`、`GiB/s` です。互換性のある単位は比較前に変換されます。互換性のない種類同士は比較できません。たとえば、1048576 B は 1 MiB と表示されますが、表では正確な値を引き続き確認できます。

方向は `lower`、`higher`、`neutral` です。neutral の列ではリグレッションは発生しません。しきい値は列内のすべての行に適用されます。絶対値とパーセンテージの両方のしきい値がある場合、いずれかを超えるとリグレッションとなり、等しい場合はリグレッションになりません。しきい値がない場合、変化は表示されますが、リグレッションによる失敗は発生しません。悪化する方向への変化のみが判定対象です。

変化率は `(new - baseline) / abs(baseline) * 100` です。ベースラインがゼロの場合、変化率はありません。絶対値のしきい値では引き続き判定できますが、パーセンテージのみのルールでは判定を保留します。比較には、後から変更された設定ではなく、対象の実行に保存された設定を使用します。

## 公式 GitHub Action を使用する

`delinoio/apps/actions/git-tracker` を、レビュー済みの完全なコミット SHA に固定します。以下のプレースホルダーを、Git Tracker の接続 ID、checkout のリビジョン、Action のリビジョンに置き換えてください。OIDC 用に `id-token: write` を付与します。代わりにリポジトリのアップロードトークンも利用できます。その場合は GitHub シークレットとして保存し、`token` を渡します。

```yaml
permissions:
  contents: read
  id-token: write
jobs:
  measure:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<reviewed-checkout-commit-sha>
      - run: ./measure.sh
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          repository-id: '019b0000-0000-7000-8000-000000000001'
          configuration: measurements.yaml
          measurements: measurements.json
          fail-on-regression: 'false'
  mark-as-done:
    needs: measure
    if: always()
    runs-on: ubuntu-latest
    steps:
      - uses: delinoio/apps/actions/git-tracker@<reviewed-action-commit-sha>
        with:
          operation: complete
          repository-id: '019b0000-0000-7000-8000-000000000001'
```

独立したジョブは、デフォルトの実行 ID `repository_id/run_id/run_attempt` を共有し、重複しない行をアップロードできます。再実行には新しい実行 ID を使用します。Actions OIDC ではデフォルトの識別情報が必要です。カスタム実行 ID は、リポジトリトークンを使用する呼び出し元向けです。OIDC 認証情報が接続済みリポジトリに属するプルリクエストのジョブでは、Action の `baseline` 入力を設定して、明示的な完全コミット SHA を使用できます。 フォークからの OIDC アップロードは PR の head に限定され、ベースラインの上書き指定や、上流の push 履歴への書き込みはできません。

各アップロードジョブは、自身がアップロードした行のみを判定します。デフォルトでは、リグレッションは報告されますが CI は失敗しません。リグレッション発生時にそのジョブを失敗させるには、`fail-on-regression: 'true'` を設定します。比較できない場合でも CI は失敗しません。完了ジョブは測定の終了を示すだけで、CI の成功・失敗・キャンセル状態を送信したり、集計結果に基づくゲート判定を行ったりするものではありません。すべてのジョブがスキップされた場合は、空の完了操作も有効です。

ネットワークエラーと一時的な API 障害では、最大 3 回再試行します。デフォルトでは、再試行後もエラーが続くとジョブは失敗します。代わりに警告を出して成功させるには、`warn-on-api-error: 'true'` を設定します。PR コメントの失敗は警告のみで、保存済みデータを無効にしたり、それ自体で CI を失敗させたりすることはありません。Action は詳細リンクをログに出力し、Job Summary を書き込みます。

1 件の PR コメントに、PR の最新コミットに対して最後に登録された実行の累積結果が反映されます。過去の実行は引き続き Web の履歴で確認できます。

## Connect API を呼び出す

API のオリジンは `https://git-tracker.api.delino.io` です。Connect の JSON リクエストでは、`Content-Type: application/json` と `Connect-Protocol-Version: 1` を使用します。管理者は、将来の有効期限の設定が必須であるリポジトリトークンを発行し、リポジトリ管理から取り消すことができます。

```sh
curl --fail-with-body \
  'https://git-tracker.api.delino.io/gittracker.v1.GitTrackerService/Upload' \
  -H "Authorization: Bearer ${GIT_TRACKER_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' \
  --data-binary @upload.json
```

`upload.json` には `context`、`dataset`、`rows` を含めます。

```json
{
  "context": {
    "repositoryId": "019b0000-0000-7000-8000-000000000001",
    "executionId": "my-historical-run",
    "commit": "0123456789012345678901234567890123456789",
    "branch": "main"
  },
  "dataset": {
    "id": "size",
    "name": "Size",
    "columns": [{ "id": "bytes", "name": "Bytes", "unit": "B", "direction": "DIRECTION_LOWER", "absoluteThreshold": "1024" }]
  },
  "rows": [{ "id": "bundle", "name": "Bundle", "values": { "bytes": "1048576" } }]
}
```

同じ `context` を指定して `/gittracker.v1.GitTrackerService/Complete` を呼び出します。PR のアップロードには `pullRequest` を含め、PR のベースブランチと head コミットを使用します。`baselineCommit` では、明示的なベースラインの完全な SHA を指定します。過去のコミットにも同じアップロード API を使用します。送信前に、十進数の文字列を JavaScript の `Number` を介して変換しないでください。

アップロードまたは完了で送信するテキストに、NUL（`\u0000`）文字を含めないでください。Git Tracker は、該当するフィールド名を示すクライアントエラーで拒否します。その他の対応する Unicode テキストおよび制御文字は引き続き有効です。

## 実行と比較のルール

最初のアップロードで、その実行における各データセットの設定が固定されます。その後に異なる設定を指定すると拒否されます。既存の行を同一の数値で繰り返し送信する操作は冪等です。競合する値は拒否されます。バッチはアトミックです。無効な行や競合する行がある場合、そのリクエストのデータは一切保存されません。

データはすぐに**測定中**として表示されます。代表結果になるのは完了後のみです。コミットの代表結果は、リグレッションのある実行も含め、完了済みの実行のうち最後に登録されたものです。古い実行が遅れて完了しても、それより新しく登録された完了済み実行を置き換えることはありません。完了操作を繰り返しても、完了時刻や順序は変わりません。

新たな測定データが保存されないまま 6 時間が経過すると、未完了の実行は**中断**状態になります。同一データの再送信では、このタイマーはリセットされません。完了済みおよび中断済みの実行は、それ以降のアップロードを拒否します。中断済みの実行は完了操作も拒否します。代わりに新しい実行を開始してください。データは削除するまで保持されます。

自動 PR 比較では、最初のアップロード時に merge-base コミットと、そのコミットの代表となる完了済み実行を固定します。ベースラインがない場合、後からアップロードされても利用不可のままです。自動 push 比較では、各行について個別に第 1 親の祖先をたどり、最初のアップロード時点までに完了していた、測定済みの最も近い祖先を使用します。後続のジョブも同じ基準時点を使用します。表には、実際の参照元となった各コミットと実行が示されます。明示的なベースライン SHA による比較では、行単位で祖先にフォールバックしません。

Web サイトの 2 コミット比較では、選択された各コミットについて、完了済みのブランチ実行のうち最後に登録されたものを優先します。そのコミットに完了済みのブランチ実行がない場合は、そのコミットの完了済みプルリクエスト実行のうち最後に登録されたものを使用します。選択された比較対象の実行に保存されているデータセット設定を使用します。新しい行や列、欠落しているデータ、互換性のないデータは比較できず、リグレッションによる失敗の原因にはなりません。削除されたベースラインデータは復元されません。存在しない行は、完了前は未収集、完了後は欠落として扱われます。

グラフでは、第 1 親の順序でコミットを等間隔に配置します。測定をスキップしたコミットをまたいで実際の測定点を結び、値を引き継いだり生成したりすることはありません。データセット、ブランチ、列、項目、日付、コミット範囲で絞り込めます。正確な値や、キーボードでアクセス可能な実行リンクを確認するには、データ表を使用してください。

## 削除とトラブルシューティング

管理者は確認操作の後、リポジトリの測定値、データセット、または 1 件の実行を完全に削除できます。存在しない実行や、現在の測定値がないデータセットを削除すると、対象が見つからなかったことが報告されます。データセットの削除は、そのデータセットを含んでいた実行にのみ影響します。他の実行では引き続きそのデータセットをアップロードできます。ベースラインの測定値が削除された比較は利用不可になります。一方、ベースラインにそのデータセットが元々含まれていなかった場合は、新しいデータとして扱われます。Delcore がスペースの削除を確定すると、Git Tracker はそのスペースの接続、トークン、設定、履歴を削除します。

権限エラーが発生した場合は、選択したスペースと現在の Git Tracker ロールを確認してください。アップロードが競合する場合は、実行の識別情報、データセットの設定、行の値がすべて揃っていることを確認してください。中断済みまたは完了済みの実行には、新しい実行 ID を使用してください。ネットワークやサーバーのエラーの場合は再試行し、サポートを求める際に備えてレスポンスの相関 ID を保存してください。公開の報告でトークン、認証情報、非公開の測定値を共有しないでください。

PR 実行の測定値は引き続き確認できますが、上流ブランチのグラフの測定点や自動ベースラインとしては使用されません。これにより、フォークの測定値が、共有されているコミット SHA のベースラインブランチのデータや設定を置き換えることを防ぎます。
